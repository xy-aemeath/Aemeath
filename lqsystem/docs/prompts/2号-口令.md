## T4 多 offer 选一个（D7，全场最难）

```
先读 CLAUDE.md、docs/contracts.md、docs/rules.md、docs/roles/2.md。

我是 2 号。做 T4：多个 offer 只能选一个。这是全项目最关键的一段，请严按照下面做。
只改 routes_mentor.py 和 static/my-offers.html。

【做什么】
1. 有 2 个以上 pending 时，每个 offer 显示"选择这个"按钮
2. 点"选择这个" → 该 offer 变 confirmed，该学生本轮其他 pending 全部变 declined
3. 已 confirmed 的显示"已确认"，不能再点
4. 底部"放弃全部机会"按钮，点前二次确认，调 POST /api/offers/decline-all

【要写的接口】
POST /api/offers/{offer_id}/confirm
POST /api/offers/decline-all   body: {"student_id":1}

【必须做到（规则 R9/R11/R12）】
- confirm 时先 SELECT 查这个 offer 的 status
- 不是 pending 就直接返回 {"ok":false,"msg":"该 offer 已失效或已处理"}，一个字都不许改
- "查状态 + 改本条 + 改其他 pending" 三步必须在同一个事务里（BEGIN ... COMMIT）
- 在事务代码上方写中文注释：// 以下三行必须在同一事务内
- 任何异常要 rollback

【临时自检接口（演示前我会让你删）】
在 routes_mentor.py 里加 GET /api/_selftest/t4?student_id=1
用两个线程同时调用 confirm 逻辑（针对同一个 offer），返回两次结果，例如：
{"ok":true,"data":{"results":["success","fail"],"confirmed_count":1}}

【完成定义】
1. 手工造数据：给 student_id=1 插 2 个 pending offer（mentor 1 和 2）
2. curl "http://127.0.0.1:8000/api/_selftest/t4?student_id=1"
   → 结果里必须恰好 1 个 success、1 个 fail，且 confirmed_count = 1
3. 查数据库：student 1 本轮 confirmed 恰好 1 条，其余是 declined
4. 对一个已经 confirmed 的 offer 再 confirm → {"ok":false,"msg":"该 offer 已失效或已处理"}
5. 连点 5 次同一个按钮（用 curl 循环 5 次）→ confirmed_count 仍是 1

【自检，做完再回我】
- 启动服务，按上面 5 条跑，把真实输出全贴给我
- 不满足就自己改，改完重跑，直到全过
- 列出你改了哪些文件，并单独贴出那段事务代码（我要看注释）

不要问"这样可以吗"，跑通再来。
```

**你回来只检查：** `/api/_selftest/t4` 的结果是不是恰好 1 成功 1 失败；那段事务代码有没有 `BEGIN/COMMIT`；它贴出的改动清单。

> 这一步如果你只做一件事，就做这个：**跑那个 selftest，看是不是只有 1 个成功。**

## T5 递补（D8）

```
先读 CLAUDE.md、docs/contracts.md、docs/rules.md、docs/roles/2.md。

我是 2 号。做 T5：递补队列。
只改 routes_mentor.py 和 static/mentor.html。

【做什么】

2. 导师页下半部分显示递补队列，每行有"上移/下移"两个按钮
3. 写一个函数 handle_offer_released(offer_id, new_status)：
   - 当 offer 变成 declined 或 expired 时调用
   - 找该导师该轮 waitlist 里 rank 最小的学生
   - 给他发一个新的 pending offer
   - 把他从 waitlist 删掉
   - 队列空了就什么也不做，不许报错（规则 R13/R14）

【要写的接口】
GET  /api/mentor/{mentor_id}/waitlist
POST /api/mentor/{mentor_id}/waitlist     body: {"student_id":1,"round":1}
POST /api/waitlist/{id}/move              body: {"direction":"up"|"down"}

【完成定义】
1. 把 student 3 加入 mentor 1 的递补队列 → GET waitlist 返回 1 条，rank=1
2. 把 student 4 也加进去 → rank=2
3. 手动把一个 student 1 的 offer 改成 declined（或用 decline-all）
   → 查 waitlist：student 3 已被移出；查 offers：student 3 有一条 pending
4. waitlist 空了之后再触发一次 release → 返回 ok，不许 500
5. 连点两次"上移" → rank 顺序正确，不会乱

【自检，做完再回我】
- 启动服务，按上面 5 条跑，贴真实输出
- 不满足就自己改，改完重跑，直到全过
- 列出你改了哪些文件

不要问"这样可以吗"，跑通再来。
```

**你回来只检查：** 学生 3 是不是真的收到了新 offer；waitlist 空了之后有没有 500。
